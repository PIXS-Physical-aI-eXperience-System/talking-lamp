# 젯슨 → 파이 재생이 안 되던 원인 (해결)

파트 C(음성) / 최승원 · 2026-09-16
대상: PR #4 `codex/jetson-pi-middleware` 의 오디오 경로

**해결됐다. 원인은 발행 간격이었다.**

프레임을 몰아서 보내면 브리지가 순서를 뒤집어 처리한다. 20 ms 간격으로
보내면 정상이다. 아래 "진짜 원인" 을 볼 것.

마이크는 처음부터 정상이었다. `/lamp/audio/capture` 가 50 Hz 로 들어오고
STT 도 동작했다.

## 진짜 원인 — 몰아 보내면 순서가 뒤집힌다

브리지는 `ReentrantCallbackGroup` 과 다중 스레드 실행기를 쓴다. 구독 콜백이
병렬로 돌기 때문에, 프레임이 한꺼번에 도착하면 **서로 다른 스레드가 순서를
뒤집어 처리한다.** `PcmFrameValidator` 는 통과한 프레임에서만 `next_sequence`
를 올리므로, 한 번 뒤집히면 이후가 전부 `out_of_order` 로 거부되고 첫 거부에서
스트림 전체가 죽는다.

우리는 "재생 시각보다 0.5초까지 앞서 보내도 된다" 고 해뒀고, 그래서 25프레임이
순식간에 나갔다. **모든 프레임을 20 ms 간격으로 보내니 소리가 났다.**

### 어떻게 갈랐나

가설을 다섯 번 세워 다섯 번 틀린 뒤에야 최소 재현을 만들었다
(`ros/playback_probe.py`). 마이크도 판단부도 상태 기계도 없이, 톤 프레임을
20 ms 간격으로 발행하는 것이 전부인 스크립트다. 그것이 소리를 내자 경로가
멀쩡하다는 것이 확정됐고, 우리 노드와의 차이는 발행 간격 하나였다.

**증상이 같은 채로 원인만 다섯 번 바뀌는 동안 변수를 줄이지 않은 것이 잘못이다.**
이런 증상에서는 최소 재현을 먼저 만들 것.

## 그 과정에서 함께 고친 것들

아래는 전부 실제 결함이었고 고쳤지만, 소리가 안 나던 직접 원인은 아니었다.

- 재생 토픽 QoS 를 `SENSOR_DATA`(BEST_EFFORT)로 발행해 구독자와 맞지 않았다.
  메시지가 한 개도 나가지 않았다 — 이것도 단독으로 치명적이었다.
- 목표 수락 전에 발행해 버려졌다.
- 두 스레드가 같이 발행해 순번이 겹쳤다.
- 스트림마다 순번 카운터를 나누지 않아 이전 스트림과 섞였다.

## 남아 있는 구조적 문제 — 프레임이 송신기가 생기기 전에 버려진다

`lamp_device_bridge/node.py`

```python
def _playback_frame(self, message):
    sender = self._playback_sender
    if sender is None or message.stream_id != self._playback_stream:
        return          # 조용히 버린다
```

`_playback_sender` 는 목표 **실행** 단계에서 대입된다 — 파이에 `audio.play.start`
를 보내고, `PlaybackSender` 를 만들고, `start()` 한 다음이다.

그런데 **수락은 실행보다 먼저**다. 우리는 `send_goal_async` 의 수락 콜백에서
프레임을 발행했고, 그 시점에는 `_playback_sender` 가 아직 `None` 이라 전부
버려졌다. 아무 로그도 남지 않는다.

### 관측이 전부 들어맞는다

| 관측 | 설명 |
| --- | --- |
| 파이의 UDP 수신 누계가 29 에서 변하지 않음 | RTP 가 한 개도 안 나갔다 |
| `playback exited with -2` | 파이 파이프라인이 데이터를 못 받아 재생 상태에 도달하지 못했고, 드레인 때 보내는 SIGINT 에 그대로 죽었다 |
| `playback exited with 1` | 같은 원인의 다른 종료 양상 |
| `success=True code=drained` 인데 무음 | 파이프라인이 형식적으로만 종료 |

`src/device/audio.py` 의 드레인은 `SIGINT` 를 보내고 `returncode != 0` 이면
실패로 본다. `gst-launch -e` 는 재생 상태였다면 SIGINT 에 EOS 를 내고 0 으로
끝나지만, 한 번도 데이터를 못 받았으면 그냥 신호에 죽는다(-2).

### 우리 쪽 대응

수락 후 1.5초 기다렸다 발행한다. **임시방편이다.** 브리지가 준비됐다는 신호가
없다. `PlayAudio` 피드백(`received_sequence`)을 기다리는 편이 맞지만, 그
피드백은 프레임이 도착해야 나오므로 순환이다.

`udpsink` 소켓이 열리는 것을 보고 출발하려 했으나 안 된다. `udpsink` 는 소켓을
`connect` 하지 않고 `sendto` 로 보내므로 `/proc/net/udp` 에 상대 주소가 남지 않는다.

## 저쪽에 필요한 것

0. **프레임이 몰려 와도 순서를 지킬 것.** 지금은 구독 콜백이 병렬로 돌아
   순서가 뒤집히고, 한 번 뒤집히면 스트림이 통째로 죽는다. 클라이언트가
   20 ms 간격을 정확히 지켜야만 동작한다 — 그 요구가 문서에 없다.
1. **송신기가 생기기 전 프레임을 버리지 말고 담아둘 것.** 또는 준비됐음을
   알릴 것 — 지금은 클라이언트가 알 방법이 없다.
2. **버릴 때 로그를 남길 것.** 조용히 버려서 어디서 사라지는지 보이지 않았다.
3. **재생 파이프라인의 stderr 를 버리지 말 것.** `src/device/audio.py` 의
   `_spawn` 이 `stderr=DEVNULL` 이라 GStreamer 오류를 아무도 볼 수 없다.
4. **재생 실패가 캡처를 죽이지 않게 할 것.** 재생이 한 번 실패하면 그 뒤로
   `speech_id` 가 안 붙거나 캡처가 아예 멈춘다. 서비스 재시작이나 재부팅이
   필요하다. 실사용에서 한 번만 실패해도 램프가 귀머거리가 된다.
5. **서비스가 정상 종료되지 않는다.** `stop-sigterm timed out` 후 매번 SIGKILL
   된다. 그렇게 죽으면 USB/ALSA 상태가 정리되지 않아 다음 기동이 더 나빠진다.
6. **device 데몬이 motion 없이 못 버틴다.** motion 을 끄면 1~2초마다
   `motion socket failed` 경고를 쏟다가 결국 서비스가 failed 로 간다.
   오디오만 켜고 시험할 방법이 필요하다.

## 확인된 것

- 스피커와 ALSA 는 정상이다. 파이에서
  `speaker-test -D plughw:CARD=L16K6Ch,DEV=0 -t sine -f 440` 하면 소리가 난다.
- 우리가 보내는 프레임은 계약대로다 — 16 kHz 모노 `pcm_s16le`, 640바이트,
  순번 0 부터 1씩, 마지막에 빈 EOS 프레임 하나.
- 마이크 경로는 정상이다. 50 Hz, 지터 1 ms 미만, STT 동작.
