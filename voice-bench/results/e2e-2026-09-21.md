# 실제 장비 전 구간 실측 — 파이 마이크 → 젯슨 → 파이 스피커

2026-09-21 / 파트 C(음성) / 최승원

지금까지 각 조각은 재봤지만 **사람이 실제로 말을 걸어 대답을 듣는 것**은
처음이다. 그 과정에서 버그 네 개가 나왔고 전부 실기기에서만 보이는
것이었다.

## 한 줄

**대화가 끝까지 돈다.** 부르면 깨어나고, 받아쓰고, 대답이 스피커로 나온다.
응답 지연은 **말이 끝나고 2.3초**(LLM 없음, 예열 후).

남은 문제는 웨이크워드다 — 학습에 없던 목소리 42%, 대화 중 헛깨움
0.40회/분. 자세한 것은 `wake-2026-09-17.md`.

## 응답 지연

말이 끝난 것으로 판정된 순간부터 첫 소리까지.

| 구간 | 첫 턴 | 예열 후 | |
| --- | --- | --- | --- |
| 발화 끝 판정 | 0.60s | 0.60s | 고정 (`--end-silence`) |
| STT | 2.61s | **0.70~1.19s** | 버퍼 길이 × RTF 0.35 |
| 응답 생성 | 0.00s | 0.00s | LLM 붙이면 여기가 는다 |
| TTS 첫 문장 | 5.22s | **0.91s** | |
| 합계 | **8.03s** | **2.29s** | |
| 송신 대기 | — | — | 0.6초지만 TTS 와 겹쳐 공짜 |

### 첫 턴 8초는 전부 예열 비용이었다

CUDA 커널 선택과 그래프 최적화가 첫 호출에 몰리고, transformers
토크나이저가 그때 HF Hub 를 친다 — 모델을 다 올려놓고도 네트워크를
기다린다. 적재할 때 미리 치르게 했다(`Tts.warmup`, `Stt.warmup`).

토크나이저는 `models/melo-ko-onnx/tokenizer` 에 이미 있는데도 Hub 를 쳤다.
데모장 네트워크에 휘둘릴 이유가 없어 `HF_HUB_OFFLINE` 으로 끊었다.

### TTS 는 고정비 + 길이 비례

맥 CPU 실측:

| 글자 | 합성 | 오디오 |
| --- | --- | --- |
| 2 | 0.39s | 1.09s |
| 6 | 0.64s | 1.82s |
| 12 | 1.03s | 2.89s |
| 20 | 1.43s | 3.91s |
| 32 | 2.31s | 6.32s |

**고정비 0.26초 + 글자당 64 ms.** 그래서 첫 문장을 쉼표에서 쪼개면 전체
합성 시간은 늘어도 첫 소리는 빨라진다(12자를 6+6 으로 쪼개면 1.03 → 0.64초).
아직 넣지 않았다 — 끊어 읽는 느낌이 나고, 예열 후 0.91초면 급하지 않다.

### 깎은 것과 안 깎이는 것

**꼬리 무음을 STT 에 안 넣는다.** 발화가 끝났는지 보려고 기다린 0.6초를
그대로 받아쓰고 있었다. 파이가 "말 아님" 이라고 표시한 구간이라 버려도
잃을 게 없고, STT 시간은 버퍼 길이에 비례한다. 약 0.2초.

**송신 대기 0.6초는 이미 공짜다.** `SPEAK_BEGIN` 을 합성 전에 보내므로
노드가 자는 동안 TTS 가 돈다. 처음에 깎을 수 있다고 봤는데 틀렸다.

**남은 카드**: 발화 끝 판정 0.6 → 0.4초 (`--end-silence 0.4`). 확실히
0.2초 벌지만 말하다 숨 쉬면 끊긴다. 기본값은 그대로 뒀다.

## barge-in — 구조적으로 가능하다

**처음 확인했다.** 재생 중에도 마이크 프레임이 온다.

```
말하는 동안 마이크 271프레임  바닥 -52.2 dB  최고 -37.0 dB  대비 15.1 dB
```

프레임이 0개면 파이가 재생 중 캡처를 끊는다는 뜻이고 그러면 barge-in 은
불가능하다. 그게 아니었다. **파이 쪽에 요청할 것 없다.**

### 램프가 자기 목소리에 놀라 자기 말을 끊었다

파이가 `success=False code=cancelled` 를 돌려줬는데, 취소한 것은 우리였다.
노드에서 취소를 부르는 길은 `BARGE_IN` 하나뿐이다.

에코 제거를 통과하고 남은 자기 목소리가 바닥 대비 **15.1 dB** 까지
올라가는데 끼어듦 판정선이 **12 dB** 였다.

20 dB 로 올렸다 — 자기 목소리(15.1) 위로 5 dB, 사람이 실제로 끼어들 때
(직전 실측 28 dB) 아래로 8 dB 여유다. **사람이 실제로 끼어드는 것은 이
장비에서 아직 안 재봤다.** 안 걸리면 `--rise-db` 로 낮출 것.

기본값이 `BargeInDetector` 와 `VoiceAgent` 두 곳에 있어서 한쪽만 고치고
다 고친 줄 알았다. 시험이 "임계 12dB" 로 잡아냈다. 상수 하나로 모았다.

### 짧은 대답에는 barge-in 이 안 걸린다

판정을 시작하기까지 1.3초가 필요하다(소리가 스피커에 닿기를 기다리는
1.0초 + 바닥을 잡는 0.3초). 1.3초보다 짧은 대답은 그 전에 끝난다.
끊을 것이 없으니 문제는 아니지만, 그 턴의 `대비` 값은 의미가 없다
(`바닥 미정` 으로 찍힌다).

## 실기기에서만 나온 버그 넷

### ① 큐가 빈 뒤 몰아 보내서 재생이 통째로 죽었다

```
프레임 167개(3.3초 분량)를 8.7초에 보냈다
재생 결과 success=False code=out_of_order
```

`t0` 를 스트림 시작에 한 번만 잡고 `due = t0 + seq*20ms` 로 갔다. 큐가 차
있을 때는 맞지만, TTS 가 다음 문장을 만드는 동안 `q.get()` 에서 막히면
시간만 가고 `seq` 는 안 는다. 그 뒤 프레임이 오면 `due` 가 한참 과거라
**밀린 만큼 몰아 보낸다.**

브리지는 `ReentrantCallbackGroup` + `MultiThreadedExecutor` 라 몰아 보낸
것을 병렬 콜백이 뒤집고, 검증기는 받아들인 프레임에서만 `next_sequence` 를
올리므로 **한 번 뒤집히면 스트림 전체가 죽는다.**

따라잡지 않는다. 한 프레임 넘게 밀렸으면 일정을 지금으로 다시 잡는다.
어차피 보낼 소리가 없어서 늦은 것이라 잃는 게 없다.

계산을 `next_due()` 로 떼어내 ROS 없이 시험한다(`bench/pacing_test.py`).

### ② 재생이 실패하는 순간 노드가 죽었다

```python
lvl = self.get_logger().info if r.success else self.get_logger().error
lvl(f"재생 결과 ...")
```

rclpy 는 **호출 위치로 심각도를 캐싱한다.** 같은 줄에서 info 를 쓰다가
error 를 쓰면 `ValueError: Logger severity cannot be changed between calls`
가 나고, 그것이 executor 를 타고 올라와 노드가 통째로 죽는다.

**성공만 하는 동안에는 안 보이다가 한 번 실패하는 순간 죽는다.** 두 줄로
나눴다.

### ③ "발화 0.0초 모음" 은 거짓말이었다

`self._buf` 를 비운 **뒤에** 길이를 재고 있었다. 늘 0.0 으로 찍혀서,
실제로 얼마나 모았는지 모르는 채 원인을 찾아야 했다. 진단 로그가 틀리면
진단이 그만큼 늦어진다.

### ④ 모델이 "픽" 을 안 듣고 있었다

사용자가 "스야" 만 말해도 깨어난다고 알려줬다. 재보니 "픽" 을 잘라내도
99%, 절반 넘게 잘라내도 92% 깨어났다. 자세한 것은 `wake-2026-09-17.md`.

## 리뷰 반영 (2026-09-21, PR #7)

세 가지가 지적됐고 전부 하드웨어 없이 재현·수정·시험했다.

### ① 재생이 끝나기 전에 말하기 상태를 벗어났다

프레임을 소켓으로 다 보낸 직후 대기로 갔다. 그런데 노드는 받은 프레임을
20 ms 간격으로 발행하고, 파이 재생 버퍼는 그보다 늦게 빈다. **스피커에서는
소리가 나는데 상태는 대기**라, 그 사이에 끼어들어도 barge-in 이 안 걸렸다.

`PlayAudio` 액션의 실제 결과를 노드가 판단부로 돌려주고(`SPEAK_DONE`),
그것을 받고서야 말하기를 끝낸다. 노드가 신호를 못 주는 경우(구버전·죽음)
영영 말하기로 남지 않도록 보낸 오디오 길이 + 5초를 상한으로 둔다.

시험 ⑥⑦⑧ — 전송 완료 후에도 말하기 유지, 그 구간의 barge-in, 성공·실패·
취소 각각의 상태 정리, 신호가 안 올 때 상한 뒤 풀리는 것.

### ② 수락 응답 전에 들어온 취소가 사라졌다

`cancel_goal_async()` 를 `goal_handle` 이 있을 때만 불렀다. 목표를
보내고 수락 응답이 오기 전에 barge-in 이 나면 핸들이 없어 취소가 전달되지
않는다. 로컬 발행만 멈추고 **액션 서버 쪽 목표는 살아서 오디오와 EOS 를
기다린다** — 다음 재생이 `audio_busy` 로 거부될 수 있다.

`cancel_pending` 을 두고 `_goal_accepted()` 에서 바로 취소한다.

시험 `bench/node_test.py` ② — 목표 전송 → 수락 전 취소 → 수락 →
수락된 핸들에 `cancel_goal_async()` 가 불리는지, 상태가 정리되는지.

### ③ 마지막 오디오 프레임과 EOS 가 붙어 나갔다

일반 프레임은 20 ms 일정을 지키는데 EOS 만 마지막 프레임 직후 바로
발행했다. 브리지가 `ReentrantCallbackGroup` + `MultiThreadedExecutor` 라
두 콜백이 겹쳐 실행될 수 있고, EOS 가 먼저 처리되면 마지막 프레임이
`out_of_order` 로 거부돼 파이가 드레인을 못 끝낸다.

**실기기에서 역전을 본 적은 없다.** 다만 간격을 지키는 것이 20 ms 밖에
안 드니 확인되지 않은 경합을 남겨 둘 이유가 없다. EOS 도 `next_due()` 를
거친다.

콜백 직렬화는 브리지 쪽 코드라 우리가 못 건드린다. 순번 검증은 이미
브리지가 하고 있고, 그 검증이 역전에 걸리는 것이 바로 이 문제다. 우리
쪽에서 할 수 있는 것은 간격을 벌리는 것이다.

시험 `bench/node_test.py` ③ — 순번이 1씩 늘고, EOS 가 마지막 하나이며,
어느 간격도 붙어 있지 않은지. 20 ms 를 딱 맞춰 요구하지는 않는다 —
절대 일정이라 한 프레임이 늦으면 다음 간격이 그만큼 짧아지고(실측 18.7 ms),
막으려는 것은 그런 흔들림이 아니라 여러 프레임을 마이크로초 안에 쏟는
것이다. 고치기 전 EOS 간격은 0.0 ms 였다.

### 실기기에서 아직 확인 못 한 것

- 재생 중 끼어들면 실제 스피커가 멈추는지
- 재생 시작 직후 취소해도 정상 종료되는지
- 취소 뒤 다음 대화가 정상으로 시작되는지
- 반복 중 `audio_busy` 나 `out_of_order` 가 안 나는지

### ④ 앞 스트림의 늦은 결과가 지금 재생을 끝냈다 (2차 리뷰)

```
0초  A 재생 시작
1초  사용자가 끼어들어 A 취소 요청
4초  A 가 아직 안 끝났지만 상한 3초가 지나 B 시작
5초  A 의 취소 결과 도착 → 공용 재생 상태를 완료로 바꿈
                          → 재생 중인 B 까지 끝난 것으로 처리
```

`_goal_accepted` 와 `_goal_result` 가 어느 스트림의 콜백인지 몰랐다.
취소 처리는 최대 10초까지 걸릴 수 있으므로 3초 상한을 넘는 상황이 실제로
생긴다.

**①번 수정이 이것을 더 나쁘게 만들었다.** `_goal_result` 가 이제
`SPEAK_DONE` 까지 보내므로, A 의 늦은 결과가 **B 의 턴을 조기 종료**시킨다 —
방금 고친 ①번 버그가 다른 경로로 되살아난다.

두 방법 중 **식별자** 쪽으로 갔다. "A 가 끝날 때까지 B 를 안 시작" 은 A 가
영영 안 끝나면 대화가 멈춘다 — 3초 상한이 원래 그래서 있다.

- `functools.partial` 로 콜백에 스트림 id 를 묶는다. 지난 스트림의 결과는
  기록만 하고 상태를 건드리지 않는다. 지난 스트림이 뒤늦게 수락되면 그
  목표만 취소한다.
- 상한이 지나 넘어갈 때 남은 목표를 취소한다. 안 그러면 액션 서버에 살아
  남아 다음 목표가 `audio_busy` 로 거부된다.

**판단부에도 같은 창이 하나 더 있었다.** 노드가 스트림 id 로 걸러도, 턴이
바뀌는 사이(판단부가 `_play_done` 을 비운 뒤 `SPEAK_BEGIN` 을 보내기 전)에
앞 턴의 결과가 도착하면 노드 쪽에서는 아직 앞 스트림이 현재라 안 걸러진다.
`SPEAK_DONE` 에 발화 id 를 실어 판단부가 자기 턴의 것인지 본다.

시험 `node_test.py` ④ 와 `agent_test.py` ⑨. 둘 다 거르기를 없애서 실제로
실패하는지 확인했다 — `SPKD` 가 B 로 가는 것과 앞 턴 신호가 지금 턴을
끝내는 것이 각각 잡힌다.

## 전체 점검 (2026-09-23)

리뷰 두 번을 필드 하나씩 막으며 반영하다가, 처음부터 끝까지 스레드별로
다시 따라갔다. **리뷰 시나리오는 막혔는데 같은 종류가 일곱 개 더 있었다.**
고치기 전에 전부 시험으로 재현해 진짜인지 먼저 확인했다.

| | 어디 | 무엇 | 재현 |
| --- | --- | --- | --- |
| N1 | 노드 | 발화 id 를 `SPEAK_BEGIN` 받자마자 노드 필드에 적음. B 가 A 를 기다리는 3초 사이에 A 의 결과가 오면 **B 의 이름으로** 완료를 보냄 → B 가 시작도 전에 끝남 | `['turnB']` |

| N3 | 노드 | 목표 거부·서버 없음이면 완료를 안 보냄 → 판단부가 상한까지 멈추고 다음 재생도 3초 지연 | 알림 `[]` |
| N4 | 노드 | 파이가 재생 도중 실패로 끝내도 다음 재생 전까지 죽은 스트림에 계속 발행 | 4개 |
| N5 | 노드 | 앞 프레임이 OS 스케줄링으로 늦으면 다음 간격이 0 에 가까워짐 — **두 프레임이 붙어 나감** | 60번에 1번 0.1ms |
| A1 | 판단부 | 끼어든 앞 턴의 대기가 상한에 걸려 풀리는 순간 **지금 말하는 턴을 대기로** | `상태 대기` |
| A2 | 판단부 | 앞 턴이 TTS·LLM 에서 막혀 있다 다음 턴 시작 뒤 깨어나면 **다음 턴 스트림에 소리를 섞고 끝 신호로 재생을 끊음** | `['SPKE']` |

N1 이 가장 심각했다. 리뷰 시나리오는 A 의 결과가 3초를 **넘어** 오는
경우인데, N1 은 3초 **안에** 오는 경우라 더 흔하다.

N5 는 흔들리는 시험을 쫓다 나왔다. 처음엔 "1~2ms 흔들림" 이라며 기준을
낮췄는데 그 가정이 틀렸다. 흔들림이 아니라 실제로 두 프레임이 붙어 나간
것이었다.

### 원인은 하나였다

**재생마다 따로 있어야 할 상태를 공용 필드로 들고, 새 재생이 시작될 때
덮어썼다.** 끼어들면 앞 재생의 스레드와 콜백이 한동안(취소가 10초까지
걸린다) 살아 있어서, 그것들이 다음 재생의 필드를 건드린다.

필드 하나씩 막으면 다음 수정 때 또 샌다. 구조를 바꿨다.

- **노드**: 재생마다 `Stream` 객체. 액션 핸들·발행 큐·수락·취소·발화 id 가
  전부 그 안에 있고, 콜백에는 그 객체를 묶어 넘긴다. "지금 재생이 끝났다"
  (`play_done`) 는 지금 재생만 세운다 — 그 판정과 재생 교체는 잠금으로 묶었다.
- **판단부**: 턴마다 `_Turn` 객체. 멈춤·완료·보낸 길이가 그 안에 있다.
  보내기는 지금 턴의 주인일 때만 하고(`_send_as`), 턴 교체와 같은 잠금을
  쓴다. 대기로 가는 것도 주인만 한다.
- **발행**: 절대 일정에 더해 연속 두 발행 사이 최소 10ms.

### 확인

**변이 시험** — 고친 곳을 하나씩 되돌려 시험이 실제로 잡는지 봤다.
안 잡히는 시험은 아무것도 안 지킨다.

- 노드 9개 전부 잡힘
- 판단부 6개 전부 잡힘
- 발행 최소 간격 잡힘

처음 돌렸을 때 노드에서 셋이 안 잡혔다. 둘은 앞 단계에서 이미 막혀
검사가 중복이었고(안전망으로 남기고 그 검사만 직접 찌르는 시험을 넣었다),
하나는 **시험이 약했다** — 발행 스레드가 루프에 들어가기 전에 취소해서
다른 검사에 걸렸던 것이다.

**이음 시험** — `integration_test.py` 가 판단부와 노드를 실제 코드 그대로
이어 리뷰 시나리오를 끝까지 돌린다. 처음 짤 때 가짜 서버가 EOS 전에
`drained` 를 줬는데, 실제 파이는 그럴 수 없다. 그 불가능한 순서가 N4 를
보여 줬다.

**반복** — 스레드 타이밍에 기대는 시험이라 네 개를 30번씩 돌렸다.
전부 30/30.

**정적 확인** — 시험은 `__init__` 을 건너뛰므로 거기 오타가 있어도 못
잡는다. 읽는 속성이 전부 어딘가에서 대입되는지 AST 로 확인했다.

### 실기기에서 볼 것

- 끼어들면 실제 스피커가 멈추는지
- 재생 시작 직후 취소해도 정상 종료되는지
- 취소 뒤 다음 대화가 정상으로 시작되는지
- **취소가 3초 안에 안 끝날 때 다음 재생이 정상인지**
- 반복 중 `audio_busy` / `out_of_order` 가 안 나는지
