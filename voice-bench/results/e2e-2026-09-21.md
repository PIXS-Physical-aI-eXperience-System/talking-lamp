# 실제 장비 전 구간 실측 — 파이 마이크 → 젯슨 → 파이 스피커

2026-09-21 / 파트 C(음성) / 최승원

지금까지 각 조각은 재봤지만 **사람이 실제로 말을 걸어 대답을 듣는 것**은
처음이다. 그 과정에서 버그 네 개가 나왔고 전부 실기기에서만 보이는
것이었다.

## 한 줄

**대화가 끝까지 돈다.** 부르면 깨어나고, 받아쓰고, 대답이 스피커로 나온다.
응답 지연은 **말이 끝나고 2.3초**(LLM 없음, 예열 후).

남은 문제는 웨이크워드다 — 학습에 없던 목소리 42%, 대화 중 헛깨움
0.40회/분. 자세한 것은 `wake-2026-09-17.md`.

## 응답 지연

말이 끝난 것으로 판정된 순간부터 첫 소리까지.

| 구간 | 첫 턴 | 예열 후 | |
| --- | --- | --- | --- |
| 발화 끝 판정 | 0.60s | 0.60s | 고정 (`--end-silence`) |
| STT | 2.61s | **0.70~1.19s** | 버퍼 길이 × RTF 0.35 |
| 응답 생성 | 0.00s | 0.00s | LLM 붙이면 여기가 는다 |
| TTS 첫 문장 | 5.22s | **0.91s** | |
| 합계 | **8.03s** | **2.29s** | |
| 송신 대기 | — | — | 0.6초지만 TTS 와 겹쳐 공짜 |

### 첫 턴 8초는 전부 예열 비용이었다

CUDA 커널 선택과 그래프 최적화가 첫 호출에 몰리고, transformers
토크나이저가 그때 HF Hub 를 친다 — 모델을 다 올려놓고도 네트워크를
기다린다. 적재할 때 미리 치르게 했다(`Tts.warmup`, `Stt.warmup`).

토크나이저는 `models/melo-ko-onnx/tokenizer` 에 이미 있는데도 Hub 를 쳤다.
데모장 네트워크에 휘둘릴 이유가 없어 `HF_HUB_OFFLINE` 으로 끊었다.

### TTS 는 고정비 + 길이 비례

맥 CPU 실측:

| 글자 | 합성 | 오디오 |
| --- | --- | --- |
| 2 | 0.39s | 1.09s |
| 6 | 0.64s | 1.82s |
| 12 | 1.03s | 2.89s |
| 20 | 1.43s | 3.91s |
| 32 | 2.31s | 6.32s |

**고정비 0.26초 + 글자당 64 ms.** 그래서 첫 문장을 쉼표에서 쪼개면 전체
합성 시간은 늘어도 첫 소리는 빨라진다(12자를 6+6 으로 쪼개면 1.03 → 0.64초).
아직 넣지 않았다 — 끊어 읽는 느낌이 나고, 예열 후 0.91초면 급하지 않다.

### 깎은 것과 안 깎이는 것

**꼬리 무음을 STT 에 안 넣는다.** 발화가 끝났는지 보려고 기다린 0.6초를
그대로 받아쓰고 있었다. 파이가 "말 아님" 이라고 표시한 구간이라 버려도
잃을 게 없고, STT 시간은 버퍼 길이에 비례한다. 약 0.2초.

**송신 대기 0.6초는 이미 공짜다.** `SPEAK_BEGIN` 을 합성 전에 보내므로
노드가 자는 동안 TTS 가 돈다. 처음에 깎을 수 있다고 봤는데 틀렸다.

**남은 카드**: 발화 끝 판정 0.6 → 0.4초 (`--end-silence 0.4`). 확실히
0.2초 벌지만 말하다 숨 쉬면 끊긴다. 기본값은 그대로 뒀다.

## barge-in — 구조적으로 가능하다

**처음 확인했다.** 재생 중에도 마이크 프레임이 온다.

```
말하는 동안 마이크 271프레임  바닥 -52.2 dB  최고 -37.0 dB  대비 15.1 dB
```

프레임이 0개면 파이가 재생 중 캡처를 끊는다는 뜻이고 그러면 barge-in 은
불가능하다. 그게 아니었다. **파이 쪽에 요청할 것 없다.**

### 램프가 자기 목소리에 놀라 자기 말을 끊었다

파이가 `success=False code=cancelled` 를 돌려줬는데, 취소한 것은 우리였다.
노드에서 취소를 부르는 길은 `BARGE_IN` 하나뿐이다.

에코 제거를 통과하고 남은 자기 목소리가 바닥 대비 **15.1 dB** 까지
올라가는데 끼어듦 판정선이 **12 dB** 였다.

20 dB 로 올렸다 — 자기 목소리(15.1) 위로 5 dB, 사람이 실제로 끼어들 때
(직전 실측 28 dB) 아래로 8 dB 여유다. **사람이 실제로 끼어드는 것은 이
장비에서 아직 안 재봤다.** 안 걸리면 `--rise-db` 로 낮출 것.

기본값이 `BargeInDetector` 와 `VoiceAgent` 두 곳에 있어서 한쪽만 고치고
다 고친 줄 알았다. 시험이 "임계 12dB" 로 잡아냈다. 상수 하나로 모았다.

### 짧은 대답에는 barge-in 이 안 걸린다

판정을 시작하기까지 1.3초가 필요하다(소리가 스피커에 닿기를 기다리는
1.0초 + 바닥을 잡는 0.3초). 1.3초보다 짧은 대답은 그 전에 끝난다.
끊을 것이 없으니 문제는 아니지만, 그 턴의 `대비` 값은 의미가 없다
(`바닥 미정` 으로 찍힌다).

## 실기기에서만 나온 버그 넷

### ① 큐가 빈 뒤 몰아 보내서 재생이 통째로 죽었다

```
프레임 167개(3.3초 분량)를 8.7초에 보냈다
재생 결과 success=False code=out_of_order
```

`t0` 를 스트림 시작에 한 번만 잡고 `due = t0 + seq*20ms` 로 갔다. 큐가 차
있을 때는 맞지만, TTS 가 다음 문장을 만드는 동안 `q.get()` 에서 막히면
시간만 가고 `seq` 는 안 는다. 그 뒤 프레임이 오면 `due` 가 한참 과거라
**밀린 만큼 몰아 보낸다.**

브리지는 `ReentrantCallbackGroup` + `MultiThreadedExecutor` 라 몰아 보낸
것을 병렬 콜백이 뒤집고, 검증기는 받아들인 프레임에서만 `next_sequence` 를
올리므로 **한 번 뒤집히면 스트림 전체가 죽는다.**

따라잡지 않는다. 한 프레임 넘게 밀렸으면 일정을 지금으로 다시 잡는다.
어차피 보낼 소리가 없어서 늦은 것이라 잃는 게 없다.

계산을 `next_due()` 로 떼어내 ROS 없이 시험한다(`bench/pacing_test.py`).

### ② 재생이 실패하는 순간 노드가 죽었다

```python
lvl = self.get_logger().info if r.success else self.get_logger().error
lvl(f"재생 결과 ...")
```

rclpy 는 **호출 위치로 심각도를 캐싱한다.** 같은 줄에서 info 를 쓰다가
error 를 쓰면 `ValueError: Logger severity cannot be changed between calls`
가 나고, 그것이 executor 를 타고 올라와 노드가 통째로 죽는다.

**성공만 하는 동안에는 안 보이다가 한 번 실패하는 순간 죽는다.** 두 줄로
나눴다.

### ③ "발화 0.0초 모음" 은 거짓말이었다

`self._buf` 를 비운 **뒤에** 길이를 재고 있었다. 늘 0.0 으로 찍혀서,
실제로 얼마나 모았는지 모르는 채 원인을 찾아야 했다. 진단 로그가 틀리면
진단이 그만큼 늦어진다.

### ④ 모델이 "픽" 을 안 듣고 있었다

사용자가 "스야" 만 말해도 깨어난다고 알려줬다. 재보니 "픽" 을 잘라내도
99%, 절반 넘게 잘라내도 92% 깨어났다. 자세한 것은 `wake-2026-09-17.md`.
