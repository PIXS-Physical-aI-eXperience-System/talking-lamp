## 결론 (VLM 단독 기준, 잠정)

- one_tile+short(32토큰) 워밍 후 응답 4~7초 — 음성 어시스턴트로 버틸 만한 수준.
  baseline(multi-tile, 128토큰) 28초는 실사용 불가.
- 로딩 65~70초 — 상시 프로세스 상주 필수. 설계 F단계(상태별 프로세스 언로드/재기동)와
  충돌 여지 있음, F단계 설계 시 이 로딩 비용을 반드시 반영해야 함.
- system peak 5.67~6.08GB (VLM단독). idle 시스템 자체가 ~2.3~2.5GB 먹으므로 VLM
  증분은 약 3.2~3.8GB. 7.2GB 통합 게이트 기준 남는 여유 1~1.5GB로 STT/TTS/모션
  동시 상주는 빠듯해 보임 — 통합 실측 전까지 미확정.
- one_tile 강제 시 baseline과 응답 내용이 달라짐(디테일 소실/다른 환각 소지) —
  타일 축소의 품질 영향 정식 평가 필요, 이번 측정은 정성적 관찰일 뿐.
- baseline system peak(6.08GB)가 설계문서 기존 기록치(6.1GB, RAM-경량화-설계.md
  10행)와 일치 — 측정 방법 신뢰도 확인.

## F단계: 상태별 언로드/재기동 (2026-09-11 추가)

`docs/RAM-경량화-설계.md` F단계("상태별 모델 프로세스 종료/재기동") 실측. 기존 프로파일(load_s 65~70s)은 매번 fp16→nf4를 즉석 양자화하는 비용이 대부분이라는 가설을 세우고, `tools/save_quantized.py`로 한 번 양자화한 체크포인트를 SSD(`/mnt/ssd`, ext4, 469G)에 저장한 뒤 `tools/wake_latency.py`로 "호명 → 로딩 → 첫 응답"을 재현.

| | 기존(즉석 bnb 양자화) | 사전양자화 체크포인트(SSD) |
|---|---|---|
| 재적재(load) | 65~70s | 5.9~7.5s |
| 첫 추론(콜드, CUDA 커널 컴파일 포함) | 20~42s | 15.7~22.7s |
| 호명→첫응답 합계 | 85~108s | **40.6~42.8s** |
| 체크포인트 크기 | - | 2.1G (SSD) |
| 프로세스 종료 후 메모리 반환 | 97~103% (baseline~short_en) | 100% (2.00→2.00GB) |
| system peak | 5.67~6.08GB | 5.28GB |

**결론**: 재적재 시간은 사전양자화로 65~70s→6~8s(약 9배)로 확 줄었지만, 첫 추론이 여전히 15~23초 걸림 — 이건 로딩이 아니라 **프로세스를 새로 띄울 때마다 CUDA 커널을 처음부터 JIT 컴파일하는 비용**이라 추정됨(웜업 추론은 3~9초인데 콜드 첫 추론만 유독 김). 그 결과 호명→첫응답이 여전히 40초대 — 노트파일이 기대한 "SSD라 2~4초"에는 한참 못 미침. 프로세스 완전 종료 시 메모리는 100% 반환됨(누수 없음), 이건 F단계 전제("아이들 때 내려놓기") 자체는 유효하다는 뜻.

첫 추론 시간은 반복 실행할수록 22.7s → 15.7s → 14.6s로 줄어듦 — CUDA 커널 디스크 캐시(`~/.nv/ComputeCache`, 기본 활성)가 웜업되는 효과로 보임. 즉 기기를 한동안 쓰고 나면 콜드스타트가 ~14~15s 선에서 안정화될 걸로 추정되고, 그럼 호명→첫응답도 30초 초반대(8+15≈23~30s)까지 내려갈 가능성 있음. 그래도 노트파일 기대치(2~4s)에는 한참 못 미침 — 이 잔여 14~15s는 로딩이 아니라 프로세스를 새로 띄울 때마다 CUDA 컨텍스트/커널을 처음부터 다시 준비하는 비용이라, F단계를 실사용 가능하게 하려면 프로세스를 완전히 죽이지 않고 CUDA 컨텍스트는 유지한 채 가중치만 내렸다 올리는 방식("종료" 대신 "일시정지")을 검토해야 함. 미검증.

## 통합 스택 실측: VLM + STT + TTS 동시 (2026-09-11 추가)

`voice-bench/JETSON-측정.md`(C/최승원)가 "아직 확인하지 못한 것"으로 남겨둔 항목 —
"VLM과 GPU를 동시에 쓸 때, 통합 메모리라 서로 밀어낼 수 있다" — 를 실측함.
STT/TTS는 voice-bench 확정 구성 그대로 사용 (STT: faster-whisper small/CUDA/
int8_float16, TTS: MeloTTS ONNX VITS fp32+BERT int8/CUDA, 전용 venv
`voice-bench/venvs/melo-onnx`, sm_87용 자체 빌드 onnxruntime-gpu/ctranslate2).
VLM은 SSD 사전양자화 체크포인트(`/mnt/ssd/internvl3_5-2b-nf4`) + one_tile.

**1차 시도(`tools/combined_run.sh`, 셋 다 t=0에 동시 실행)**: 시스템 피크 5.29GB —
근데 타임라인 까보니 STT(0~6s)·TTS(6~20s)가 VLM의 무거운 torch/CUDA 임포트
(23~49s) 전에 이미 끝나버려서 실제로는 거의 순차 실행이었음. 이 숫자는 신뢰 못함.

**2차 시도(`tools/combined_run2.sh`, VLM 시작 15초 뒤에 STT+TTS 투입)**: 진짜 겹침.

| | 값 |
|---|---|
| **시스템 피크** | **7.09GB** |
| 게이트(7.2GB) 대비 여유 | **0.11GB** |
| swap | 0 (in/out 페이지 전부 0) |
| idle 복귀(스크립트 전체 종료 후) | 2.03GB (before 대비 100% 반환) |

타임라인 상 특이점: STT(~6s)·TTS(~21s)는 t=15~36s 사이에 이미 프로세스 종료됐는데,
피크(7.08GB)는 한참 뒤인 t=50~56s(VLM 혼자 돌던 구간)에 찍힘. VLM 단독 피크는
평소 5.3~5.8GB인데 여기선 그보다 1.3~1.8GB 높게 유지됨 — STT/TTS가 반납한
GPU/시스템 메모리가 VLM이 GPU를 계속 쓰는 동안엔 즉시 반영 안 되고 지연되는
것으로 추정(통합 메모리 드라이버 레벨 회수 지연). 스크립트 전체가 끝나면
idle로 100% 돌아옴 — 진짜 누수는 아니고 지연임. 이 "부풀려진 상태로 몇십 초
유지"가 F단계(온디맨드 언로드/재기동) 설계에서 안전 여유를 잡을 때 고려해야 할
변수임.

**결론**: 7.09GB < 7.2GB로 **게이트 통과하긴 함**. 근데 여유가 0.11GB뿐이라
검출기(D, 김아현이 아직 실측 안 한 [임시] 0.3~0.7GB)를 넣는 순간 확실히 넘음.
이번 측정도 이미지 1장·짧은 발화 1턴·32토큰 답변 기준의 최선 케이스임 — 더 긴
답변, 문장 여러 개짜리 TTS, VLM 멀티턴 등 현실적 워스트케이스는 아직 안 잼.

## 검출기(D) 실측 (2026-09-11 추가)

D(김아현) 담당인 검출기가 지금까지 [임시] 0.3~0.7GB 추정치로만 있었음(README 43행,
파트-분배.md). 실측함 — YOLO11n(COCO 사전학습, ultralytics), 별도 venv
(`/mnt/ssd/detector-venv`, PyPI aarch64 torch 2.14.0+cu130 — JetPack 전용
빌드 아님. sm_87 "공식 미지원" 경고 뜸, 근데 CPU와 GPU 결과가 완전 동일해서
계산 자체는 안 깨짐, 최적화 커널이 없어 **느릴 뿐**).

| | 값 |
|---|---|
| 시스템 RAM 증분(idle 대비) | **1.09GB** |
| CUDA 피크 | 0.074GB (거의 GPU 안 씀) |
| 속도 | 4.7 FPS (경고대로 최적화 커널 없어서 노트파일 기대치 30~100 FPS에 한참 못 미침) |
| 탐지 정확도 | 이번 테스트 이미지(파워뱅크 근접샷)엔 안 맞는 사진이라 낮은 확신도(0.29~0.48)로 book/cup/chair/dining table/bowl 등 엉뚱하게 찍음 — COCO에 "파워뱅크" 클래스가 없어서. 책상+책/키보드/머그 같은 실제 타겟 장면에서 재검증 필요 |

**중요한 caveat**: 1.09GB는 순수 PyTorch(ultralytics 기본 경로) 기준임 — torch·torchvision·opencv·matplotlib 풀스택이 다 로드됨. voice-bench가 TTS에서 이미 겪은 것과 같은 패턴("바닥을 만드는 게 모델이 아니라 torch 런타임")일 가능성 높음. 노트파일이 기대한 "런타임 ~0.2GB"는 ONNX/TensorRT로 내보낸 뒤의 수치고, 지금 잰 건 그 최적화 전 값임 — 실제 배포판은 이보다 작아질 걸로 예상되나 미검증.

### 통합 스택 + 검출기 합산 (VLM+STT+TTS 실측 7.09GB 기준)

| 검출기 구성 | 검출기 증분 | 합계 | 7.2GB 게이트 |
|---|---|---|---|
| 지금 잰 PyTorch 그대로 | +1.09GB | **8.18GB** | **한참 초과, 8GB 물리 한계도 넘음** |
| ONNX/TensorRT 최적화 후 (노트파일 추정) | +0.2~0.5GB | 7.29~7.59GB | **여전히 초과** |

**결론: 검출기를 최적화해도 게이트를 못 넘길 가능성이 높음.** VLM+STT+TTS만으로 이미 여유 0.11GB였는데, 검출기가 아무리 가벼워져도(노트파일 최선 추정 0.2GB) 최소 7.29GB — 이 통합 스택 전체를 다시 줄이지 않는 한 7.2GB 게이트는 이론상 못 지킴. D(김아현)에게 ONNX/TensorRT 변환 실측 우선순위로 전달 필요.

## 검출기 ONNX 최적화 (2026-09-11 추가)

torch 기반 ultralytics(위 항목)는 무거움 확인됨. voice-bench와 같은 패턴으로
torch를 걷어내고 순수 onnxruntime(sm_87용 자체 빌드, `voice-bench/venvs/melo-onnx`
재사용)으로 추론하도록 YOLO11n을 ONNX로 export(NMS 내장, `nms=True`)해서 재측정.

| | PyTorch(ultralytics) | ONNX(onnxruntime, torch 없음) |
|---|---|---|
| 시스템 RAM 증분 | 1.09GB | **0.72GB** (-34%) |
| 속도 | 4.7 FPS (sm_87 비공식 지원 경고) | **37.8 FPS** (노트파일 기대치 30~100과 일치) |

torch 런타임 자체가 바닥을 만든다는 voice-bench의 결론이 검출기에도 그대로 적용됨.
노트파일의 낙관적 추정(~0.2GB)은 아마 TensorRT 엔진 기준으로 보이며, 이번 onnxruntime
CUDA EP 값(0.72GB)보다 더 줄이려면 TensorRT 변환이 추가로 필요함 — 미검증.

### 통합 스택 재계산

| 구성 | 합계 | 7.2GB 게이트 |
|---|---|---|
| VLM+STT+TTS(7.09GB) + 검출기 PyTorch(+1.09GB) | 8.18GB | 초과 (8GB 물리 한계도 넘음) |
| VLM+STT+TTS(7.09GB) + 검출기 ONNX(+0.72GB) | **7.81GB** | **여전히 초과** |

ONNX로 줄여도 아직 7.2GB를 0.6GB 넘음. 검출기를 아무리 최적화해도 VLM+STT+TTS
자체가 이미 여유 0.11GB뿐이었던 게 근본 원인 — 이 통합 스택 전체(특히 VLM)를
더 줄이거나, F단계 온디맨드 로딩으로 동시 상주 자체를 피해야 함.

## F단계 개선: CUDA 컨텍스트 유지한 채 가중치만 내렸다 올리기 (2026-09-11 추가)

기존 F단계 측정(프로세스 완전 종료 후 재기동)은 호명→응답 39~43초였음. 병목이
로딩이 아니라 "새 프로세스의 CUDA 커널 JIT 컴파일"이라는 가설을 검증하려고,
**프로세스는 살려두고 가중치 텐서만 `del`+`empty_cache()`로 반납한 뒤 같은
프로세스 안에서 다시 로드**해봄 (`tools/pause_resume_test.py`).

| | 기존 F단계(프로세스 재기동) | 컨텍스트 유지(가중치만 반납/재로드) |
|---|---|---|
| 재적재 | 5.9~8.0s | 6.1s (동일) |
| 첫 추론(재적재 직후) | 15~23s (콜드 JIT) | **6.3s (웜 속도 그대로!)** |
| 호명→응답 합계 | 39~43s | **~12.4s** (3.2배 개선) |

가설 확인됨 — 같은 프로세스 안에서는 CUDA 커널이 이미 컴파일돼 있어서
재적재 후 첫 추론이 콜드가 아니라 웜으로 나옴. 노트파일이 기대한 "2~4초"엔
아직 못 미치지만 40초대에서 12초대로 확 줄었음.

**메모리 쪽 확인함 — 공짜가 아님.** 20초까지 유휴를 늘려봐도 시스템 사용량이
**~3.65GB에서 더 안 내려가고 그대로 유지됨** (진짜 idle 기준 2.0~2.4GB 대비
+1.3~1.6GB 상시 부담). `del`+`empty_cache()`가 CUDA 컨텍스트/PyTorch 캐싱
할당자가 쥐고 있는 예약 메모리까지는 못 돌려줌 — 프로세스를 완전히 죽여야만
(기존 F단계 방식) 100% 반납됨.

**트레이드오프 정리:**

| | 프로세스 완전 종료(기존 F단계) | 프로세스 유지, 가중치만 반납("일시정지") |
|---|---|---|
| 유휴 시 시스템 사용량 | 2.0~2.4GB (100% 반납) | **~3.65GB (반납 안 됨, 상시 부담)** |
| 호명→응답 | 39~43s | **~12.4s** |

빠른 응답이 필요하면 유휴 때도 +1.3~1.6GB를 계속 물고 있어야 함 — 이게 통합
스택 예산(7.2GB)에서 상시로 깎여 나간다는 뜻. B(오케스트레이터)가 "느린 첫
응답 vs 상시 메모리 부담" 중 뭘 우선할지 정책으로 결정해야 하는 사안임.

## 파일

- `baseline.json`, `one_tile.json`, `short_ko.json`, `short_en.json`: `bench_vlm_ram.py` 원본 출력 (로딩/추론 시간, CUDA 피크, RSS 표본, 생성 텍스트).
- `*-system.json`: `ram_probe.py` 출력 (프로세스 전체 수명 동안 `/proc/meminfo` 기반 시스템 RAM 샘플).
- `*.log`: 실행 stdout/stderr 원본.

## 800MB 여유 RAM 게이트 재평가 및 재실행 하네스 (2026-09-12)

`MemAvailable` **최소 800MB(10진), swap I/O 0, 자식 프로세스 정상 종료**를 한 회의
합격 조건으로 명시했다. 여유 RAM의 상한은 두지 않는다. 더 많이 남는 실행은 더
안전하기 때문이다.

기존 결과를 같은 판정기로 다시 평가한 결과는 다음과 같다.

| 후보 | 최소 MemAvailable | 판정 | 피드백 |
|---|---:|---|---|
| 2B + STT/TTS 강제 동시 실행 (`integrated_stack2`) | 762.6MB | 실패 | 목표보다 37.4MB 부족. 실제 데이터 의존관계에도 맞지 않아 폐기 |
| 단계가 사실상 분리된 실행 (`integrated_stack`) | 2,558.3MB | 통과 | 상태별 직렬 실행의 가능성을 확인했으나 당시 스크립트는 타이밍 우연에 의존 |
| 2B, 1타일, 영어 32토큰 | 2,168.1MB | 통과 | 입력 이미지의 의자를 정확히 설명함 |
| 1B, 1타일, 영어 32토큰 | 3,770.7MB | RAM 통과 | 입력 이미지의 전원 어댑터를 정확히 설명함. 2B와 이미지가 달라 이 행만으로 품질 우열 판정 불가 |

최종 실행 정책은 STT가 끝난 뒤 VLM을 시작하고, VLM 응답이 나온 뒤 TTS를
시작하는 것이다. 세 단계 사이에 데이터 의존성이 있으므로 동시에 띄울 이유가
없다. 메모리 검증용 `tools/run_dialogue_memory.sh`가 이를 명시적으로 보장하며
2B 사전 양자화 체크포인트, 1타일, 32토큰 설정을 사용한다. 이 스크립트는 단계별
벤치 입력을 실행하며 STT 결과를 VLM에 전달하거나 VLM 답을 TTS에 전달하는 제품
파이프라인은 아니다. `tools/repeat_ram_experiment.py`는 새
프로세스로 기본 3회 반복하고 단 한 번이라도 800MB 아래로 내려가면 실패한다.

품질 비교에는 같은 이미지가 필수다. 기존 `short_*`의 2B 이미지 해시는
`5eaba7…`이고 1B는 `24efd9…`이므로 모델 간 품질 비교 자료로 쓰지 않는다. 같은
전원 어댑터 이미지를 쓴 `qa_demo.json`과 `qa_demo_1b.json`에서는 영어 단문은 둘 다
핵심 물체를 맞혔다. 한국어 답변은 2B도 한자 혼입으로 실패했고, 1B는 한자 혼입에
더해 핵심 개념 누락까지 발생했다. 따라서 현재 품질 게이트 기준에서 **한국어 직접
출력은 두 모델 모두 불합격**이며, 2B 선택은 아직 최종 확정이 아니다.
`tools/evaluate_vlm_quality.py`가 이미지 해시, 필수 개념, 문자권 혼입, 깨진 문자,
연속 반복을 검사한다. 새 VLM 결과는 회차별 JSON으로 자동 저장된다.

Jetson 재실행 명령:

```bash
python tools/repeat_ram_experiment.py \
  --out-dir results/dialogue-2b-sequential --attempts 3 \
  --min-available-mb 800 --max-swap-pages 0 -- \
  bash tools/run_dialogue_memory.sh
```

기존 결과의 판정 JSON은 `goal-800mb-overlap.json`,
`goal-800mb-serialized-evidence.json`, `goal-800mb-1b-evidence.json`에 보관했다.
품질 판정은 `quality-*.json`에 보관했다.
새 직렬 스크립트 자체의 실기 측정은 Jetson SSH 인증이 복구된 뒤 위 명령으로
확정해야 한다. 검출기는 대화 상태에서 중지하고 idle/S1/S4에서만 실행하는 정책을
적용해야 한다. 검출기까지 동시에 상주시킨 최종 실측은 아직 없다.
