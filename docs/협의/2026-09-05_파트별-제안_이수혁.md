## 0. 공통 전제: 좌표계·관절 규약 (A·B·C·D 모두 해당)

**배경.** 각 파트가 주고받는 위치·각도 값의 기준이 안 맞으면 통합 때 전부 다시 짜야 함. E가 이미 코드(`src/motion/`)에 정의해 둔 걸 기준으로 제안.

**내 제안.**

- **좌표계 `lamp_base`**: 원점 = 램프 베이스 바닥 중심, +x = 앞쪽(사용자 방향), +z = 위, +y = 왼쪽. 단위 미터. 모든 3D 위치(얼굴·물체·조명 타겟·소리 방향)를 이 프레임으로 통일.
- **관절 각도 배열**: `[base_yaw, base_pitch, elbow_pitch, wrist_roll, wrist_pitch]` 순서 고정 (서보 ID 1~5), 단위 라디안, 부호·원점은 `sim/lelamp_arm.xml` (MuJoCo) 기준.
- 레이어 간 통신은 **절대 관절 각도로만** 함 (속도·상대변위 안 섞음).
- **타임스탬프**: 모든 이벤트에 `stamp` (단조 증가 초, `time.monotonic()`).

**상대가 결정·확인할 것.**

- **B**: 이 좌표계·관절 규약을 이벤트 스키마에 반영
- **D**: 3D 타겟점·얼굴 위치를 `lamp_base` 프레임으로 출력
- **C**: DOA를 `lamp_base` 프레임 기준 방위/고도로 출력
- **A**: 행동 태그가 관절 각도를 직접 만들지 않음 (프리미티브 이름만)

## 1. E ↔ B (김태현 / 시스템통합) [최우선]

### 1-1. 런타임 스텁 + 이벤트 스키마 착수 상태

**배경.** 진행-순서 인수인계 2번. B의 런타임 스텁이 A·C·D·E의 출발선. E는 지금 `MotionRuntime`을 자체 루프로 돌리고 있어서, B 스키마가 나오면 그 위로 옮겨야 함.

**내 제안.**

- B가 **이벤트 스키마 + 런타임 스텁(껍데기)** 을 이번 주 안에 1차 배포
- E의 `MotionRuntime` 공개 API를 B의 라우팅 대상으로 그대로 채택 제안:

```python
rt.observe_point(xyz, confidence, stamp)    # D 얼굴 → L1
rt.observe_bearing(origin, dir, confidence) # C DOA → L1 (S6)
rt.play_primitive(name, intensity)          # A 행동 태그 → L2
rt.place_task_light(xyz)                    # D 조명 타겟 → L3 (S1)
rt.barge_in()                               # B 말끊기 조율
rt.step()                                   # 100 Hz
```

**상대가 결정·확인할 것.**

- 이벤트 스키마 초안 공유 시점
- E의 API를 그대로 쓸지, B가 이벤트 메시지로 감쌀지
- 모션 루프(100Hz)를 B 런타임이 호출할지, E가 독립 스레드로 돌리고 이벤트만 구독할지

### 1-2. 어느 보드가 런타임을 소유하나 (Pi ↔ Jetson)

**배경.** Pi 5 + Jetson 공존이 확정됨. 이벤트 버스가 두 보드에 걸침.

**내 제안.**

- 기가비트 이더넷 직결(스위치 없이 고정 IP), 이벤트 버스 = TCP/UDP 소켓
- 역할 분담: **Pi = 실시간**(서보 버스·100Hz 궤적·블렌더·L0/L1·LED·웨이크워드) / **Jetson = AI**(VLM·STT·TTS·검출기·IK)
- IK는 Jetson에서 풀어 절대 관절 각도로 Pi에 전달 → Pi 블렌더가 합성
- 카메라·마이크·스피커 신호 전부 Pi로 집결, 베이스↔Jetson은 이더넷 1가닥
- 이벤트 버스 스키마·상태머신은 Jetson에서, Pi에 thin client

**상대가 결정·확인할 것.**

- 이더넷 소켓 기반 이벤트 버스 OK인지 (B 런타임 설계 전제)
- 상태머신(대기/청취/사고/발화)을 어느 보드에서 돌릴지
- IK를 Jetson vs Pi 어디서 풀지 (E는 Jetson 선호, 검출 결과와 같은 보드)

### 1-3. barge-in(말 끊기) 조율 로직

**배경.** C가 사용자 끼어든 발화 감지 → TTS 정지(C), A 요청 취소 + E 모션 인터럽트(B가 동시 발행).

**내 제안.**

- E의 `rt.barge_in()` = L2(프리미티브)·L3(조명 자세) 0.15초 릴리스 + 대기 자세 크로스페이드 (**이미 구현됨**)
- B는 C의 barge-in 신호를 받으면 `rt.barge_in()` 호출 + A에 취소 신호 동시 발행
- E의 L1(추종)·L0(대기 모션)은 유지 (고개는 사용자 쪽 보고 있어야 함)

**상대가 결정·확인할 것.**

- barge-in 이벤트 정의 (누가 발행, 페이로드)
- 취소 후 재개 정책 (사용자 발화 끝나면 원래 동작 복귀? 새로 시작?)

## 2. E ↔ A (주경태 / 인지) [B 경유]

### 2-1. 행동 태그 스키마·포맷

**배경.** 진행-순서 인수인계 5번. A의 행동 태그 스키마가 있어야 B가 라우팅, E가 재생. 파트-분배 미확정 항목.

**내 제안.** 대사에 태그를 섞는 방식(`<nod/>`) 말고 **대사 + 별도 행동 리스트 JSON**:

```json
{
  "speech": "안녕하세요",
  "actions": [
    {"tag": "nod", "at": 0.0, "intensity": 0.8},
    {"tag": "curious", "at": 1.2, "intensity": 0.5}
  ]
}
```

- 사용 가능한 태그(프리미티브): `nod`, `headshake`, `curious`, `excited`, `happy_wiggle`, `sad`, `shy`, `shock`, `scanning`, `wake_up`, `idle` (LeLamp CSV 11종). 필요하면 E가 추가 제작.
- 파라미터: `intensity` 0~1 (필수), `at` 발화 기준 초 (선택, 기본 0), `repeat` (선택)
- 태그가 깨지거나 없는 이름이면 E는 무시 + 로그 (전체 실패 안 함)
- "사용자 쪽 봐" 같은 시선 동작은 태그가 아니라 L1이 자동 처리 → A는 신경 안 써도 됨

**상대가 결정·확인할 것.**

- JSON 별도 리스트 방식 OK인지 (VLM 출력 안정성, A가 파서 책임)
- 태그 목록 이걸로 충분한지, 더 필요한지 (예: `agree`, `disagree`, `think`, `greet`)
- `intensity` 외에 필요한 파라미터
- S3(자연어 조명 제어) 출력 포맷: 조명 파라미터 변화량을 A가 어떻게 내보내는지 (E는 조명 제어를 서브 MCU에 위임하므로 이건 D/서브MCU와도 연결)

### 2-2. VLM 벤치마크 결과 공유

**배경.** 인수인계 1번. A의 VLM 속도·메모리 결과가 나와야 메모리 예산·모델 크기 확정. E 하드웨어에 직접 영향은 적지만 Jetson 열·전력 예산에 참고.

**상대가 확인할 것.**

- 벤치마크 결과 (속도·피크 RSS·한국어 품질) 공유 시점
- Jetson에서 VLM 구동 시 소비 전력·발열 (E의 방열 설계 입력)

## 3. E ↔ C (최승원 / 음성)

### 3-1. 마이크 = XVF3800 → C의 AEC 부담 감소

**배경.** E가 XMOS XVF3800(원형 어레이) 발주 완료. 이 칩이 하드웨어 AEC + 빔포밍 + DOA 내장.

**내 제안.**

- C의 AEC를 소프트웨어로 새로 짜지 말고 **XVF3800 내장 AEC 우선 활용** (계획서에서 "난이도 최상"으로 표시된 항목 부담이 크게 줆)
- USB Audio Class 표준이라 Pi·Jetson 양쪽에서 사운드카드로 잡힘 → ReSpeaker Pi HAT 이식 문제(H3) 없음
- 최종적으로 XVF3800은 **Jetson에 연결** 제안 (STT/TTS가 Jetson, AEC far-end reference가 같은 보드에 있어야 깔끔). baseline 단계는 Pi에 꽂아 원본 테스트
- ⚠️ AEC 동작하려면 스피커로 나가는 소리(far-end reference)를 XVF3800에 되물려줘야 함. 보드 오디오 출력/레퍼런스 경로를 C가 데이터시트에서 확인

**상대가 결정·확인할 것.**

- XVF3800 내장 AEC로 충분한지, 추가 소프트웨어 AEC 필요한지
- XVF3800을 Pi vs Jetson 어디에 붙일지 (신호처리 파이프라인 위치)
- 웨이크워드 어느 보드에서 돌릴지
- 스피커를 XVF3800 출력으로 뺄지, 별도 앰프 필요한지

### 3-2. DOA 출력 포맷 (E의 L1 입력, S6)

**배경.** 인수인계 7번. C의 소리 방향이 E의 L1 칼만 필터 입력. E의 `observe_bearing(origin, direction)` API가 이미 있음.

**내 제안.** DOA 이벤트:

```json
{
  "frame": "lamp_base",
  "direction": [0.0, 0.0, 0.0],
  "confidence": 0.9,
  "stamp": 0.0
}
```

- `direction` = 단위 벡터, 소리가 오는 방향
- `origin`은 마이크 어레이 위치 (E가 기구 좌표로 제공) → E가 `origin + range*direction`으로 가상 타겟점 만들어 칼만에 넣음
- 방위/고도(azimuth/elevation) 각도로 줘도 됨 (벡터가 편하면 벡터)
- 갱신율 10~30Hz면 충분 (칼만이 coast함)

**상대가 결정·확인할 것.**

- 방향 벡터 vs 각도
- DOA 갱신율, 신뢰도 산출 방식
- XVF3800이 2-mic면 전후 모호성 있음 → 원형 어레이로 360° 되는지 확인

### 3-3. 마이크-스피커 이격 + barge-in 타이밍

**내 제안.**

- 마이크 어레이는 스피커에서 최대한 이격 (거리가 곧 AEC 난이도). E가 헤드/베이스 배치할 때 C와 위치 협의
- barge-in: C가 TTS 즉시 정지 → B가 E에 모션 인터럽트 발행 (E는 이미 대응). 감지~정지 목표 지연을 C가 제시

**상대가 확인할 것.**

- 마이크 어레이 장착 희망 위치 (헤드 vs 베이스)
- barge-in 감지 지연 목표치

## 4. E ↔ D (김아현 / 비전) [소통 빈도 높음]

### 4-1. 조명 광학 요구사항 (E가 광원 발주하려면 필요) [시급]

**배경.** 인수인계 3번. D가 광량·배광각·색온도를 수치로 내야 E가 작업 조명 부품 발주 가능. **E는 지금 이거 대기 중.**

**내 제안.**

- D가 **필요 광량(lux @ 목표 거리), 배광각, 색온도**를 우선 산출 (다른 비전 작업보다 앞당김)
- 헤드에서 목표면까지 거리 범위, 목표면 크기도 같이
- 이 수치 나오면 E가 광원 + 방열 발주

**상대가 결정·확인할 것.**

- 광학 요구사항 산출 시점 (E 대기 항목 중 유일하게 막혀있음)
- LED vs COB, 조광 방식 (PWM?)

### 4-2. 3D 타겟점 인터페이스 (E의 IK 입력, S1)

**배경.** 인수인계 6번.

**내 제안.** 조명 타겟 이벤트:

```json
{
  "frame": "lamp_base",
  "type": "light_target",
  "pos": [0.0, 0.0, 0.0],
  "surface_normal": [0.0, 0.0, 1.0],
  "confidence": 0.9,
  "stamp": 0.0
}
```

- `pos` = 비출 목표점 (책상 위, z≈0), `surface_normal` = 목표면 법선 (선택)
- E가 IK로 헤드를 목표점 위+뒤(raking 각도)에 배치. `rt.place_task_light(pos)` 이미 구현
- 눈부심·손 그림자 회피 방향은 D가 목표점에 반영해서 주거나, `surface_normal` + 얼굴 위치를 같이 주면 E가 접근 방향 계산

**상대가 결정·확인할 것.**

- 눈부심·그림자 회피 계산을 D가 할지(목표점에 녹여서), E가 할지(법선+얼굴 받아서)
- 타겟점 갱신 방식 (이벤트 1회 vs 지속 추종)

### 4-3. 얼굴 검출 결과 (E의 L1 칼만 입력, S2)

**내 제안.** 얼굴 이벤트:

```json
{
  "frame": "lamp_base",
  "type": "face",
  "pos": [0.0, 0.0, 0.0],
  "confidence": 0.9,
  "stamp": 0.0
}
```

- `pos` = 얼굴 중심 3D
- 갱신율 ~30Hz, 검출 실패 시 이벤트 안 보내면 E 칼만이 알아서 coast (1초 후 track drop)
- 2D 박스 + 책상평면 역투영으로 3D 만드는 건 D 담당

**상대가 결정·확인할 것.**

- 얼굴 3D화를 D가 완료해서 줄지, E가 2D+깊이 받아서 할지
- 검출 갱신율, 지연

### 4-4. 카메라 하드웨어 (E가 제공)

**내 제안.**

- USB 광각 카메라 (CSI 대신. 관절 통과 배선·길이 제한 때문)
- 헤드에 장착, 베이스 Pi로 연결 → Pi가 프레임을 Jetson으로 이더넷 스트리밍
- 캘리브레이션은 D 절차 수립, E는 마운트·고정 담당
- 램프가 책상에 고정된 조건(책상평면 역투영) → E 기구가 베이스-책상 고정을 보장

**상대가 결정·확인할 것.**

- 필요 화각·해상도·프레임레이트
- 카메라 마운트 위치 (헤드 어디에)
- 책상 평면 등록 절차 (초기 1회): E 기구가 뭘 보장해야 하는지

### 4-5. S4 자리비움 판정

**내 제안.** D가 시간·신뢰도 히스테리시스로 재실 판정 → 이벤트 발행 → E가 감광(서브 MCU) + 대기 자세 모션. 복귀 시 인사 프리미티브.

**상대가 확인할 것.**

- 판정 임계 시간 (몸 잠깐 숙인 정도로 오작동 안 하게)

## 5. 전원 참여 항목 (전체)

**배경.** 조립·배선·무게 실측·통합 주차는 파트 무관 전원 참여 (파트-분배 5절).

**내 제안.**

- 3D 출력물 조립: E가 순서 정리, 실제 조립은 나눠서
- 통합 주차: S2(호명→시선→대화)부터 관통, B·C·A·E 참여. 일정 잡기
- 헤드 무게 실측: 조명·방열 붙은 뒤 E가 측정 → 모션 한계·서보 전압 재계산

**결정할 것.**

- 통합 주차 일정
- 조립 역할 분담
- 부품 배송 일정 공유 (E가 발주 내역·ETA 공유)
